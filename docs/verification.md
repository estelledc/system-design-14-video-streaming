## Executable counterexamples

- Twenty concurrent upload-open requests under one owner/key must create one video/upload; changed intent conflicts.
- Two different chunk keys racing at one offset cannot both advance it; exact winning-key replay returns the first result.
- Correct length with a wrong full digest creates no processing job.
- A recovered worker replaces the lease token; the old worker cannot commit even with an earlier nominal completion time.
- Segment/manifest objects written before a worker exit remain invisible and can be verified/reused after lease recovery.
- A ready rendition returns `404` until an explicit publication transaction selects it.
- Removing one referenced segment makes publication fail integrity and leaves the video ready/invisible.
- Repeated equal segment bytes may share a content object while retaining separate ordered manifest positions.
- A tombstone makes later origin manifest and segment observations return `410` while objects remain physically present.
- Multiple ranges fail before any `server_bytes_written` receipt.

## Process smoke target

The smoke performs this exact sequence with real processes, PostgreSQL, filesystem objects, and loopback HTTP:

1. open an upload;
2. commit chunk 1, then `SIGKILL` the API before its response;
3. restart and exactly replay chunk 1 without duplicate offset advance;
4. complete and finalize the source;
5. claim a job, write every segment/manifest, then `SIGKILL` before ready commit;
6. verify the manifest endpoint is still `404`;
7. recover the expired job with attempt 2, verify/reuse the existing objects, and commit ready;
8. verify ready is still `404`, restart the API, and explicitly publish;
9. fetch a `206` range and observe only `server_bytes_written`;
10. tombstone and observe `410` for both manifest and segment;
11. scan every child-process structured record for fixture credentials, keys, bytes, IDs, digests, and paths.
